# 논문 리뷰 작성 규격

이 저장소(`chb2066.github.io`)에 논문 리뷰를 추가할 때 따르는 규격이다.
사람이든 에이전트든 이 문서만 읽고 바로 초안을 쓸 수 있게 적었다.

읽는 순서: **2절(파일 위치와 frontmatter) → 3절(문서 구조) → 4절(서식 금지 규칙) → 7절(체크리스트)**.
4절이 이 문서의 핵심이다. 거기 적힌 것들은 전부 한 번씩 어겨서 되돌린 적이 있는 항목이다.

---

## 1. 전체 그림

- Astro 정적 사이트. `src/content/` 아래 마크다운이 그대로 페이지가 된다.
- `main` 브랜치에 push 하면 GitHub Actions 가 빌드해서 배포한다. 수동 배포 없음.
- 컬렉션 세 개
  - `src/content/reviews/` - 논문 리뷰. 이 문서가 다루는 대상
  - `src/content/knowledge/` - 기법 사전
  - `src/content/projects/` - 프로젝트 노트

로컬 확인

```bash
npm install     # 최초 1회
npm run dev     # http://localhost:4321
npm run build   # 배포 전 반드시 통과시킬 것
```

## 2. 파일 위치와 frontmatter

파일은 `src/content/reviews/<slug>.md` 하나만 만든다.
`<slug>` 는 소문자, 단어 사이는 하이픈. 그게 곧 URL 이 된다 (`/reviews/<slug>`).

```markdown
---
title: SwAV
paper: Unsupervised Learning of Visual Features by Contrasting Cluster Assignments
venue: NeurIPS 2020
authors: Caron, Misra, Mairal et al.
link: https://arxiv.org/abs/2006.09882
claim: 인스턴스 비교 대신 prototype 할당을 서로 바꿔 예측하게 하면 메모리 뱅크 없이 contrastive learning이 된다.
tags: [Self-supervised, Clustering]
tier: basic
date: 2025-06-04
draft: true
---
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `title` | O | 목록에 뜨는 짧은 이름. 보통 모델·방법 이름 (`SwAV`, `DINOv2`) |
| `paper` | | 논문 정식 제목 |
| `venue` | | `NeurIPS 2020`, `arXiv 2025` 형태 |
| `authors` | | `Caron, Misra, Mairal et al.` 형태 |
| `link` | | 논문 URL. arXiv abs 페이지 선호 |
| `claim` | O | **한 문장.** 이 논문이 주장하는 것. 목록 페이지에 이게 뜬다 |
| `take` | | 내 판단. 동의하는 곳, 아닌 곳. 없으면 생략 |
| `tags` | | 아래 6절 참고. 새 태그를 함부로 만들지 말 것 |
| `tier` | | `main` = 자세히 쓴 것, `basic` = 가볍게 정리한 것. 목록에서 두 묶음으로 나뉜다 |
| `date` | O | `YYYY-MM-DD`. 읽은 날 |
| `draft` | | `true` 면 빌드에서 빠진다. **새 글은 `true` 로 시작한다** |

`title` 과 `claim` 과 `date` 만 필수고 나머지는 없어도 빌드된다.

`draft: true` 인 글은 사이트에 안 뜬다. 내용을 다 채우고 사람이 한 번 읽은 뒤에
`false` 로 바꾸는 것이 기본 절차다. 에이전트가 임의로 `false` 로 두지 않는다.

## 3. 문서 구조

### 3.1 골격

```markdown
[논문 제목](https://arxiv.org/abs/XXXX.XXXXX)

## Abstract

**문제**

- 기존 방식이 무엇을 못 했는지
- 왜 그게 문제인지

**해결책**

- 이 논문이 무엇을 바꿨는지
- 그래서 무엇이 가능해졌는지

---

## 1. Introduction

**기존 상황**
- 항목 → 귀결

**본 논문의 기여**
1. ...
1. ...

---

## 3. Method

### 3.1 Online clustering

**입력 요소**
- ...

**붕괴 방지 - Sinkhorn-Knopp**
- ...

---

## 4. Main Results

- ...
```

### 3.2 절 번호는 논문 것을 그대로 쓴다

`## 1. Introduction`, `### 3.2 Multi-crop` 처럼 **논문의 번호와 제목을 그대로** 가져온다.
영어 제목은 영어 그대로 둔다. 번역하지 않는다.

이유는 두 가지다. 논문을 펴놓고 대조하기 쉽고, 내가 절을 새로 지어낼 여지가 없어진다.

건너뛴 절 번호는 그냥 비워둔다. `## 1` 다음에 `## 3` 이 와도 된다.
다루지 않기로 한 절은 아예 쓰지 않는다. "이 절은 생략한다" 같은 안내문도 쓰지 않는다.

### 3.3 본문은 개조식

- 문단으로 풀어쓰지 말고 항목으로 끊는다
- 리스트 항목은 음슴체로 끝낸다 (`~함`, `~됨`, `~임`)
- 인과는 `→` 로 연결한다. `라벨을 새로 붙여야 함 → 일반성이 제한됨`
- 하이퍼파라미터 값을 다 적을 필요는 없다. 다만 **입력이 무엇인지**는 적는다.
  그래서 `**입력 요소**` 블록이 자주 등장한다

### 3.4 표와 코드

- 비교는 표로. 3열 이상이거나 축이 둘이면 표가 낫다
- 수식·의사코드는 코드 펜스(` ``` `)로. 언어 태그는 `text` 또는 `python`
- 변수는 인라인 코드로 감싼다. `` `z` ``, `` `q·k` ``

## 4. 서식 금지 규칙

여기가 제일 중요하다. **전부 실제로 어겼다가 되돌린 항목이다.**

### 4.1 em dash 금지

`—` 를 쓰지 않는다. `-` 를 쓴다.

```markdown
잘못  **입력 요소** — 동일한 이미지의 두 view
맞음  **입력 요소** - 동일한 이미지의 두 view
```

문장 중간 삽입구는 `-` 로 바꾸면 한국어가 깨진다. 괄호로 돌린다.

```markdown
잘못  라벨이 비싼 도메인 - 의료, 로봇, 산업 - 에서 가치가 크다
맞음  라벨이 비싼 도메인(의료, 로봇, 산업)에서 가치가 크다
```

`–`(en dash)도 같다. 범위는 `~` 를 쓴다. `2025.07 ~ 2025.08`

### 4.2 기울임 금지

`*기울임*` 을 쓰지 않는다. 강조가 필요하면 문장을 고쳐 쓴다.

예외는 없다. `A*/D*`, `RRT*` 처럼 **이름에 붙은 별**은 기울임이 아니므로 그대로 둔다.

### 4.3 볼드는 소제목·부제에만

볼드는 **줄 머리에 오는 짧은 라벨**에만 쓴다. 판정 기준은 셋 다 만족할 것.

1. 그 줄의 맨 앞에 있을 것 (불릿·번호 뒤여도 됨)
2. 24자 이하일 것
3. 뒤가 줄 끝이거나 ` - ` 또는 `:` 로 끊길 것

```markdown
맞음  **입력 요소**
맞음  **깨지는 지점** - 입출력 차원이 같아야 한다
맞음  - **Short-range** - 8개 블록의 합집합이 약 15% 를 덮음

잘못  1. **항등함수가 기본값이 된다.** 블록을 추가해도…      (문장 통째 볼드)
잘못  1. **positive pair 만으로** 학습하는 BYOL 제안        (문장 안 강조)
잘못  | 시각 | **동등.** 시각 강건성은 RL로 오지 않는다 |      (표 안 볼드)
```

### 4.4 볼드 소제목 다음에는 빈 줄

마크다운은 줄바꿈 하나를 줄바꿈으로 치지 않는다. 이걸 빼먹으면 한 문단으로 뭉쳐 나온다.

```markdown
잘못
**문제**
full-duplex 음성 모델은 지연을 줄였지만 역할이 고정돼 있음
duplex 구조는 두 조건을 동시에 주는 방법이 자명하지 않음

  -> <p><strong>문제</strong> full-duplex … 자명하지 않음</p> 한 덩어리로 렌더된다

맞음
**문제**

- full-duplex 음성 모델은 지연을 줄였지만 역할이 고정돼 있음
- duplex 구조는 두 조건을 동시에 주는 방법이 자명하지 않음
```

줄이 하나뿐이면 빈 줄만 넣고 불릿은 안 붙여도 된다.

### 4.5 머리글은 링크 한 줄

본문 첫 줄은 논문 링크 하나다. 이모지·인용 블록·학회·저자를 붙이지 않는다.
학회와 저자는 frontmatter 에 이미 있다.

```markdown
잘못  > 📄 [**Segment Anything**](https://arxiv.org/abs/2304.02643) · ICCV 2023 · Kirillov et al.
맞음  [Segment Anything](https://arxiv.org/abs/2304.02643)
```

### 4.6 `## 정리` 절을 쓰지 않는다

"이 논문에서 가져갈 것은", "옮겨갈 만한 재료는", "다만 대가가 있다" 로 이어지는
마무리 절을 붙이지 않는다. 논문에 없는 감상이다.

한마디 덧붙일 것이 있으면 frontmatter 의 `take` 에 한 문장으로 적는다.

### 4.7 서사 전환 문장을 쓰지 않는다

내용은 없고 분위기만 잡는 줄이다. 볼드든 평문이든 쓰지 않는다.

```markdown
잘못  **여기서 문제가 갈린다**
맞음  **기존 방식의 한계**

잘못  **iBOT은 크게 두 가지 아이디어를 쓴다**
맞음  **두 가지 아이디어**

잘못  아래가 이 둘을 가능하게 하는 방법론이다.
잘못  두 가지가 중요하다.
잘못  구조가 가장 단순한데 성능이 크게 뒤지지 않는다는 것이 요지다.
       -> 전부 삭제. 앞뒤가 그냥 붙는다
```

사실을 말하는 한 줄은 괜찮다. `VOC2007 test 기준이다.`, `` `N`은 매칭된 default box의 개수다. ``

문단 끝마다 결론을 다는 습관도 같은 문제다.
`~가 중요하다`, `~는 뜻이다`, `~인 셈이다`, `~가 핵심이다` 를 반복하지 않는다.

### 4.8 그림은 넣지 않는다

논문 PDF 에서 그림을 잘라 넣지 않는다. 한 번 125장을 넣었다가 전부 뺐다.

`public/img/<slug>/01.png` 처럼 **저장소에 이미 있는 그림**만 참조한다.

```markdown
![그림](/img/clip/01.png)
```

없으면 그냥 안 넣는다. 자리 표시용 빈 이미지도 만들지 않는다.

### 4.9 용어는 논문에서 쓰는 대로

표준 기술 용어를 한국어로 옮기지 않는다. 논문을 영어로 읽는 독자가 본다.

| 쓰지 말 것 | 쓸 것 |
|---|---|
| 시각 모델 | Vision model |
| 고정 클래스 집합 | fixed class set |
| 지도 신호 / 훈련 신호 | supervised signal / training signal |
| 판별 신호 | discriminative signal |

한국어가 자연스러운 것(정규화, 손실, 학습, 추론)까지 억지로 영어로 바꾸라는 뜻은 아니다.
**논문에서 그 단어로 부르는 것**을 그대로 쓰라는 뜻이다.

### 4.10 논문에 없는 해석을 덧붙이지 않는다

"어려운 문제를 푸는 대신 쉬운 문제를 대규모로 푼다" 같은 요약은 내 말이지 논문의 말이 아니다.
논문이 한 주장과 보인 결과만 적는다.

판단을 남기고 싶으면 frontmatter 의 `take` 한 줄에 적는다.

## 5. 기존 글 고칠 때

- **frontmatter 를 임의로 바꾸지 않는다.** 특히 `draft`, `date`, `tier`
- 사람이 쓴 문장을 "더 매끄럽게" 다시 쓰지 않는다. 오타·조사 오류만 고친다
- 지운 절을 되살리지 않는다. 지워진 데는 이유가 있다

## 6. 태그

이미 쓰고 있는 태그를 먼저 찾아 쓴다. 태그마다 페이지가 생기므로 비슷한 이름이
따로 생기면 목록이 갈라진다.

현재 많이 쓰는 것

```
Self-supervised, Vision-Language, Segmentation, NLP, RLHF, Robotics,
Vision Backbone, Backbone, Transformer, Generative, Diffusion, Video, LLM,
Contrastive, Non-contrastive, Object Detection, JEPA, Calibration,
Knowledge Distillation, Retrieval, RL, Data-Centric
```

전체 목록은 이렇게 뽑는다.

```bash
grep -h '^tags:' src/content/*/*.md | tr -d '[]' | sed 's/^tags: //' \
  | tr ',' '\n' | sed 's/^ *//' | sort | uniq -c | sort -rn
```

새 태그는 기존 것으로 도저히 안 될 때만 만든다. 단수/복수, 하이픈 표기를 기존과 맞춘다.

## 7. 내보내기 전 체크리스트

```bash
npm run build          # 통과해야 한다. frontmatter 오류가 여기서 잡힌다
python docs/check.py   # 아래 스크립트
```

`docs/check.py` 가 보는 것

- `—` `–` 가 남아 있는지
- `*기울임*` 이 남아 있는지
- 볼드가 규칙 밖에서 쓰였는지
- 볼드 소제목 바로 밑에 평문이 붙어 있는지 (한 문단으로 뭉치는 자리)
- 머리글이 링크 한 줄인지
- `## 정리` 가 있는지
- 참조한 이미지 파일이 실제로 있는지
- `**` 짝이 맞는지, 코드 펜스가 닫혔는지

커밋은 무엇을 왜 바꿨는지 한국어로 적는다. 파일을 명시적으로 stage 한다.

```bash
git add src/content/reviews/<slug>.md
git commit -m "..."
```

`git add -A` 는 쓰지 않는다. 의도하지 않은 파일이 딸려 올라간 적이 있다.

## 8. 빠른 요약

새 리뷰 하나를 만드는 최소 절차.

1. `src/content/reviews/<slug>.md` 생성, frontmatter 작성, `draft: true`
2. 첫 줄에 `[논문 제목](링크)`
3. `## Abstract` 에 `**문제**` / `**해결책**` 두 블록. **각 볼드 뒤에 빈 줄**
4. 논문 절 번호를 그대로 따라가며 개조식으로 채움
5. `## 정리` 안 씀. 그림 안 넣음. 기울임 안 씀. `—` 안 씀
6. `npm run build` + `python docs/check.py` 통과
7. 사람이 읽고 `draft: false` 로 바꾸면 게시
